# Atlas — лабораторная работа №5

Клиент-серверное приложение на JavaScript и MongoDB: единый каталог книг, стран и товаров, подборки, заметки, автоматический импорт и мониторинг. Требования взяты из `task.md`.

## Запуск с отказоустойчивой MongoDB (рекомендуется для защиты)

```powershell
Copy-Item .env.example .env
docker compose -f docker-compose.ha.yaml up --build -d
```

Открыть **http://127.0.0.1:4000**. Этот вариант поднимает весь стенд: три MongoDB в replica set `atlas`, инициализатор, gateway, catalog, workspace и worker. У каждой MongoDB собственный постоянный том; порты базы и подграфов наружу не публикуются. Подготовка индексов завершается до запуска сервисов. Worker сам начинает первый импорт. Логи: `docker compose -f docker-compose.ha.yaml logs -f worker`.

При потере одного узла MongoDB оставшиеся два сохраняют большинство и автоматически выбирают primary. Драйвер использует retryable reads/writes, запись подтверждается `majority`; во время выборов возможна кратковременная задержка или ошибка запроса. Подробнее: [выборы replica set](https://www.mongodb.com/docs/manual/core/replica-set-elections/).

Это отдельный Compose-проект `atlas-ha` с отдельными томами. Данные старого одноузлового стенда автоматически не переносятся и не удаляются. Не запускайте оба gateway на порту 4000 одновременно. Все контейнеры на одном компьютере защищают от отказа отдельного процесса/узла базы; для защиты от отказа физического хоста три узла нужно разместить на разных хостах.

## Локальный запуск с одной MongoDB

Нужны Node.js **22.15+**, npm и запущенный Docker Desktop с Linux Engine.

```powershell
Copy-Item .env.example .env
docker compose up -d
npm ci
npm start
```

Открыть **http://127.0.0.1:4000**. В Compose описан **только MongoDB**; приложение запускается локально из консоли. `npm start` поднимает четыре самостоятельных процесса. Ctrl+C завершает их. MongoDB сохраняет данные в именованном томе, поэтому перезапуск контейнера не удаляет каталог.

Первый импорт запускается автоматически. До его завершения каталог доступен и постепенно наполняется. Статус, ошибки и количество записей видны на вкладке «Источники и импорт». Сбор 10 500 уникальных книг занимает несколько минут и зависит от внешнего API. Готовность к демонстрации: статус `COMPLETED`, минимум 10 000 записей, ненулевое количество у каждого из трёх источников. Ошибка источника не маскируется тестовыми данными: задача получает `FAILED`, уже собранные записи сохраняются.

Повторный запуск вручную:

```powershell
npm run import
# Или другая цель: минимум 10000, максимум 100000 уникальных книг
npm run import -- 12000
```

Одновременно разрешена одна задача. После сбоя или отмены повторная задача продолжает последнюю незавершённую с сохранённой страницы. После успешно завершённого импорта новый запуск обновляет данные с первой страницы. `AUTO_IMPORT=false` отключает автоматический первый запуск.

| Динамическое формирование | На вкладке GraphQL конструктор выбирает источник, детали и заметки; доступен редактор произвольных операций, JSON-переменных, aliases и fragments. |
| Фильтрация, сортировка, поиск, пагинация | Тип, источник, тег, диапазоны года и значения; четыре поля сортировки в двух направлениях; индексированный полнотекстовый поиск; страницы по 1–100 записей, стабильная сортировка с `_id`. |

## Архитектура

```text
Браузер ── GraphQL ── Gateway :4000 (также статические файлы)
                         ├── GraphQL ── Catalog :4001 ──┐
                         └── GraphQL ── Workspace :4002 ┤
                                                      ├── MongoDB :27017
Внешние источники ── HTTPS ── Worker (отдельный процесс) ┘
```

`Catalog` владеет каталогом и метаданными источников; `Workspace` — подборками, заметками, заданиями импорта и диагностикой. Worker забирает задания из MongoDB и собирает внешние данные. Все процессы используют одну логическую базу MongoDB: replica set в HA-варианте или standalone в упрощенном локальном варианте. Subgraph закрыты внутренним shared secret. По умолчанию HTTP слушает только loopback.

Сервисы можно запускать в отдельных терминалах:

```powershell
npm run start:catalog
npm run start:workspace
npm run start:gateway
npm run start:worker
```

Для разделения на хосты предусмотрены `MONGODB_URI`, `CATALOG_URL`, `WORKSPACE_URL` и общий `INTERNAL_SECRET`. Адрес прослушивания задается `HOST` (локально `127.0.0.1`, в контейнерах `0.0.0.0`). Для публичного развертывания также нужны TLS, аутентификация MongoDB и сетевые политики; готовый Compose рассчитан на локальный лабораторный стенд.

## Данные

1. [Open Library Search API](https://openlibrary.org/dev/docs/api/search): названия, авторы, год, языки, темы, количество изданий. Запросы последовательные, с интервалом не менее 1,1 секунды, ограниченным списком полей и User-Agent. Данные каталога опубликованы Open Library; действуют [условия источника](https://openlibrary.org/developers/licensing).
2. [mledoze/countries](https://github.com/mledoze/countries): названия стран, столицы, регионы, языки, площадь; лицензия ODbL-1.0. Площадь — числовое значение для фильтрации и сортировки стран. Отсутствующее население хранится как `null`. REST Countries v3 отключён: приложение использует проверенный открытый набор, не требующий API-ключа.
3. [DummyJSON Products](https://dummyjson.com/docs/products): учебные товары, описание, бренд, цена, рейтинг, остаток. Это демонстрационные данные внешнего сервиса, не реальные предложения магазинов.

Идентификаторы имеют префикс источника; повторный импорт обновляет записи, не размножая их. Задача завершается успешно только при наличии данных всех трёх источников, достижении цели Open Library и общего объёма минимум 10 000. Удалённые во внешних источниках записи при обновлении локально не удаляются.

## Примеры GraphQL

Точка входа: `POST http://127.0.0.1:4000/graphql`, заголовок `Content-Type: application/json`. Эти примеры также можно выполнить во встроенном редакторе.

```graphql
query Catalog($filter: EntryFilter, $page: Int!) {
  entries(filter: $filter, sort: {field: YEAR, direction: DESC}, page: $page, pageSize: 20) {
    total
    pageInfo { page totalPages hasNextPage }
    items {
      id title year
      source { name }
      authors { name }
      book { editionCount languages }
    }
  }
}
```

```json
{"filter":{"kind":"BOOK","search":"history","minYear":1900},"page":1}
```

```graphql
mutation Create { createCollection(name: "Прочитать") { id name } }
mutation Add($collectionId: ID!, $entryId: ID!) {
  addToCollection(collectionId: $collectionId, entryId: $entryId) { id name }
}
mutation Note($entryId: ID!) {
  addNote(entryId: $entryId, text: "Для дальнейшего изучения") { id text }
}
query Federation {
  collections(limit:5) {
    name
    items(limit:10) {
      id title source { name }
      notes(limit:5) { text entry { title authors { name } } }
    }
  }
}
```

Реализованы Query и Mutation. Обновление прогресса и метрик — GraphQL polling раз в 5 секунд, без WebSocket/subscription. Полнотекстовый поиск MongoDB работает по словам в названии, описании, тегах и авторах, а не по произвольной подстроке.

## Мониторинг и диагностика

Вкладка «Мониторинг» показывает heartbeat, запросы/ошибки каждого сервиса, p95 и последние spans. Для worker счётчики означают завершённые и неуспешные задачи с момента старта. Метрики агрегируются по всем сохраненным gateway spans за 5 минут, без прежнего ограничения в 2 000 spans; p95 вычисляется приближенным `$percentile`. Ответы 403/429/503 и обрывы соединений 499 учитываются на HTTP-уровне и получают trace ID. Для сервисов видны накопительные счетчики `rejected`, `rateLimited`, `overloaded` и текущий `inflight`. Телеметрия записывается с ограничением очереди и не блокирует бизнес-ответы: при полной недоступности MongoDB часть traces может быть потеряна; JSON-логи остаются в stdout. Header `x-trace-id` связывает ответ браузеру со spans шлюза и subgraph. Введите этот ID в фильтр, чтобы увидеть конкретный распределённый запрос. `parentId` subgraph указывает на span шлюза. Worker также пишет spans задачи и каждого источника; при ручном запуске они связаны с трассой мутации `startImport`.

При трёх последовательных сетевых/HTTP 5xx ошибках subgraph circuit breaker отклоняет обращения к нему на 15 секунд. После паузы допускается один пробный запрос; его успех закрывает circuit breaker. Запросы к другому subgraph продолжают работать. При выборе обязательных полей недоступного сервиса возможен стандартный для GraphQL null bubbling. Supervisor перезапускает завершившийся процесс через 3 секунды. После аварийного завершения worker задачу можно снова взять по истечении lease (90 секунд); запись страницы идемпотентна.

## Проверки

```powershell
npm run lint
npm test
npm run test:integration
npm run test:resilience
# Реальные источники, автоматический worker и 60 секунд нагрузки в отдельной временной БД:
npm run verify:live
# При запущенном приложении:
npm run test:load -- 5 50
# Третий аргумент включает тест по времени; число запросов тогда не ограничивается вторым аргументом:
npm run test:load -- 10 10000 60
```

Модульные тесты проверяют composition Federation, адаптеры, фильтры и ограничения, оценку сложности, retry/backoff, импорт 10 000 фикстур и возобновление с checkpoint. HTTP-тест без MongoDB запускает настоящие Apollo-сервисы с тестовыми resolvers и проверяет Federation, parent spans, авторизацию, rate limit и изоляцию отказа. Интеграционный тест запускает настоящий временный `mongod`, два subgraph и gateway в отдельных процессах; проверяет поиск, CRUD, федеративную вложенность, трассы и родительские spans, атомарное ограничение задач, авторизацию, rate limit и работу каталога при остановке Workspace. Тестовые три записи — только фикстуры, не наполнение приложения. В первый запуск `mongodb-memory-server-core` загружает MongoDB 8.0.17; нужен интернет. Для существующей тестовой MongoDB задайте `TEST_MONGODB_URI`; тест создаёт случайную БД и удаляет только её.

`test:resilience` запускает три настоящих mongod, аварийно завершает worker после checkpoint, проверяет продолжение той же задачи без дублей, останавливает primary и проверяет сохранность данных и запись через GraphQL после выборов. Проверяются 24 варианта индексированной сортировки и 15 секунд непрерывной нагрузки на 10 101 фикстуре. Тестовый транспорт источников существует только в `test/fixtures/worker.js`, в production его нет.

`verify:live` запускает исходные сервисы и настоящий worker, автоматически собирает минимум 10 000 книг и оба других источника, затем выполняет три нагрузки по 20 секунд (5/10/20 клиентов). Результат сохраняется в `verification/live-result.json`; временная БД удаляется, процессы останавливаются. Обычно требуется несколько минут и доступ к внешним API. Для измерения пропускной способности только в этой временной среде лимит повышен до 100 000 запросов/мин; штатные 180/мин отдельно проверены HTTP-тестами.

`test:load` выводит фактические RPS, p50/p95, успешный RPS и p95 успешных ответов отдельно, число ошибок и отказов admission control. Большие нагрузки могут ожидаемо получить HTTP 429/503. Размер и сложность запросов ограничиваются до исполнения, задержка внешнего импорта не блокирует API.

CI выполняет lint, модульные, HTTP-, интеграционные тесты и тест отказоустойчивости. Реальный внешний импорт не запускается в CI, чтобы результат CI не зависел от доступности публичных источников. Для воспроизводимой установки используйте `npm ci`: точные версии зафиксированы в `package-lock.json`.

Чтобы использовать уже запущенную MongoDB из Compose без загрузки дополнительного дистрибутива для тестов:

```powershell
$env:TEST_MONGODB_URI = "mongodb://127.0.0.1:27017"
npm run test:integration
```

Результаты текущей проверки, исправленные замечания и границы измерений — в [review-report.md](review-report.md).

## Ограничения локального стенда

Упрощенный `docker-compose.yaml` содержит одну MongoDB и не обеспечивает failover. Для проверки отказоустойчивости используйте `docker-compose.ha.yaml` или `npm run test:resilience`. При потере большинства узлов replica set запись останавливается, чтобы сохранить согласованность. Подборки общие для всех пользователей; до 100 записей в подборке; список имеет `limit` (1–100) и `offset`, интерфейс показывает страницы по 20 подборок; заметки — последние 20 для записи; задания — последние 20. GraphQL-типизация и валидация ограничивают ввод. `ADMIN_TOKEN` при необходимости защищает все мутации: введите его через кнопку «Токен доступа», хранение только в sessionStorage вкладки. Для публичного доступа нужны пользовательская авторизация и полноценная инфраструктура наблюдаемости.

## Контроль сложности и индексы

Защита и обработчик GraphQL находятся в одной цепочке Express: регистр, завершающий slash и подмаршруты не обходят rate/concurrency limit или внутренний секрет. Отключенный клиент освобождает слот после завершения его вычисления; незавершенная обработка продолжает учитываться, поэтому разрыв связи не позволяет обходить лимит.

Стоимость считается по типам составленной схемы, реальным лимитам списков и приведенным GraphQL-переменным, включая значения по умолчанию, aliases, fragments и директивы skip/include. `collections(limit:...)`, `items(limit:...)`, `notes(limit:...)` позволяют явно ограничивать разветвление. Запрос всего максимального вложенного графа может быть отклонен даже при небольшом числе фактических записей — оценка выполняется до обращения к данным. Для списка подборок используется `noteCount`, чтобы не загружать тексты всех заметок.

Сортировки `title/year/value/updatedAt` имеют индексы с согласованным направлением `_id`, а фильтры по `kind` и `sourceId` — соответствующие составные индексы. Планы проверяются в обе стороны сортировки через `explain('executionStats')`. Полнотекстовый поиск и произвольные комбинации диапазонов могут требовать дополнительной сортировки; время чтения ограничено `maxTimeMS`.
