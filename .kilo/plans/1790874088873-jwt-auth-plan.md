# План: JWT-аутентификация и роли (редактор / читатель / админ)

## Контекст

Приложение — SPA-менеджер задач (Express 4 + better-sqlite3, статический фронтенд `public/`, API `/api/tasks`). Сейчас нет аутентификации: любой может читать, создавать, удалять и переключать статус задач.

## Решения (согласованы с пользователем)

- **Роли:** `editor` (создание, изменение статуса, удаление задач), `reader` (только чтение), `admin` (права редактора + панель назначения ролей).
- **Учётные записи:** почта, логин, пароль. Открытая регистрация; новый пользователь получает роль `reader`.
- **Хранение токена:** `localStorage` + заголовок `Authorization: Bearer <token>`.
- **Первый админ:** создаётся из env-переменных при запуске (`ADMIN_EMAIL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`).
- **Хеширование паролей:** `bcryptjs` (чистый JS, без native-сборки в Docker).
- **JWT:** `jsonwebtoken`, секрет из `JWT_SECRET` (fallback для разработки — `dev-secret-change-me`), срок жизни 24 ч, refresh-токены не нужны.
- **Ограничение безопасности ролей:** админ не может изменить роль самому себе (защита от потери последнего админа).

## Зависимости

`npm i bcryptjs jsonwebtoken` (в `package.json`; `npm ci` в Dockerfile уже пересоберёт).

Также добавить в `docker-compose.yaml` переменные для админа и секрета:
`JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD` (со значениями-заглушками).

## Задачи

### 1. База данных — таблица пользователей (`src/database/db.js`)

```sql
CREATE TABLE IF NOT EXISTS users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  email TEXT NOT NULL UNIQUE,
  login TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'reader'
    CHECK(role IN ('reader', 'editor', 'admin')),
  created_at TEXT NOT NULL
);
```

После `db.exec` — сид первого админа (idempotent):
- если `ADMIN_EMAIL`/`ADMIN_LOGIN`/`ADMIN_PASSWORD` заданы и пользователя с таким `login` или `email` нет → вставить админа с хешем пароля.

### 2. Слой auth (новые файлы по существующему паттерну routes → controllers → services → repositories)

- `src/repositories/users.js` — `UserRepository`:
  - `findByLogin(login)`, `findByEmail(email)`, `findById(id)`, `findAll()`, `create({email, login, passwordHash, role})`, `updateRole(id, role)`.
- `src/services/auth.js` — `AuthService`:
  - `register({email, login, password})` — валидация: email-формат, `login` ≥ 3 симв., пароль ≥ 6 симв.; проверка уникальности email/login; хеш `bcryptjs.hash(password, 10)`; роль `reader`.
  - `login({login, password})` — поиск по login, `bcryptjs.compare`, вернуть `{ token, user }`.
  - `generateToken(user)` — `jwt.sign({ id, role, login }, JWT_SECRET, { expiresIn: '24h' })`.
  - `verifyToken(token)` — `jwt.verify`.
- `src/controllers/auth.js` — `AuthController`:
  - `register` → 201 + `{success, data: {token, user}}` или 400/409.
  - `login` → 200 + `{success, data: {token, user}}`; 401 при неверных данных.
  - `me` → 200 + `{success, data: user}` (роль из БД, не из токена — свежие данные).
- `src/routes/auth.js` — `POST /register`, `POST /login`, `GET /me` (защищён).
- `src/middlewares/auth.js`:
  - `authenticate` — читает `Authorization: Bearer <token>`, кладёт `req.user = {id, role, login}` из verify; 401 при отсутствии/просрочке/невалидности.
  - `authorize(...roles)` — 403, если роль не в списке.

### 3. Защита задач (`src/routes/tasks.js`, `src/app.js`)

- `GET /api/tasks`, `GET /api/tasks/:id` — `authenticate` (любая роль).
- `POST /api/tasks`, `PATCH /api/tasks/:id/toggle`, `DELETE /api/tasks/:id` — `authenticate`, `authorize('editor', 'admin')`.
- В `src/app.js`: подключить `routes/auth.js` на `/api/auth`; `app.use('/api/tasks', ...)` — заголовки защищаются на уровне роута.

### 4. Админ-панель — управление ролями

- `src/controllers/admin.js` — `AdminController`:
  - `getUsers` → список пользователей (id, email, login, role, created_at).
  - `updateRole` → смена роли: валидация роли, запрет изменения своей роли; 404 если пользователя нет; 400 на `PATCH /api/admin/users/:id/role` с невалидной ролью.
- `src/routes/admin.js` — `GET /api/admin/users`, `PATCH /api/admin/users/:id/role` — `authenticate`, `authorize('admin')`.
- Роль в `req.user` обновлять из БД в `authenticate` (запрос по id) — сразу отзывается доступ при понижении роли.

### 5. Фронтенд (`public/index.html`, `public/js/app.js`, `public/css/style.css`)

- **Авторизация:**
  - При загрузке: если в `localStorage` нет токена → показать экран входа/регистрации (переключаемые формы; поля email, login, пароль, подтверждение пароля при регистрации).
  - `login()` / `register()` → `fetch('/api/auth/login'|'/api/auth/register')`, сохранить токен, `GET /api/auth/me` для роли, показать приложение.
  - Кнопка «Выйти» → очистка `localStorage`, возврат к экрану входа.
  - Общий хелпер `apiFetch(url, options)` — добавляет заголовок `Authorization`; при ответе 401 → выйти, показать экран входа.
- **Роли в UI:**
  - `reader`: без формы создания задачи, без кнопок «Завершить»/«Вернуть»/«Удалить».
  - `editor`/`admin`: полный функционал задач (текущий).
  - `admin`: дополнительно пункт «Панель админа» — список пользователей (почта, логин, роль) с `<select>` роли и сохранением через `PATCH /api/admin/users/:id/role`; свою роль в списке не менять (select disabled).
- Состояние: `this.currentUser` (из `/me`), хранение токена в `localStorage('token')`.

### 6. Документация/конфиги

- Обновить `docker-compose.yaml`: блок `environment` с `JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`.
- `.env.example` (или расширение compose-комментарием) — как задать секрет и первого админа.
- `README`, если есть, в текущем репозитории отсутствует (глобально — не создавать без запроса).

## Проверка (ручная)

1. `npm start` без env → сервер поднимается; зарегистрировать пользователя → роль `reader`, задачи видны, кнопок изменения нет; прямой `POST /api/tasks` без токена → 401, с токеном читателя → 403.
2. Вход под редактором → создание/переключение/удаление задач работает; повторить запросы читателя → 403.
3. Вход под админом (env) → панель: смена роли пользователя на `editor`/`reader`; попытка смены своей роли → 400; понижение админом другого админа отзывается сразу (свежая роль из БД в `authenticate`).
4. Неверный пароль → 401; дубликаты email/login → 409/400; просроченный/подделанный токен → 401.
5. `docker compose build && docker compose up` — приложение работает, админ создаётся из env.

## Риски / примечания

- `login` — имя поля и колонки; в SQLite не является зарезервированным словом, конфликтов нет.
- Не отправлять `password_hash` в JSON-ответах — только id, email, login, role, created_at.
- При изменении роли в процессе сессии `authenticate` использует роль из БД, поэтому права меняются без перелогина.
- `better-sqlite3` синхронный — подходит для учебного объёма; новых зависимостей с native-сборкой не добавляется (`bcryptjs` чистый JS).
